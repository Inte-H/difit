# 에이전트가 답할 지적이 생기면 끝나는 wait 명령으로 알리고, Claude Code 세션에는 메시지로도 넣는다

지금까지 에이전트는 `difit comment get`을 다시 돌려야 리뷰어의 지적을 알았다. 백그라운드로 띄운 명령은 끝날 때만 에이전트를 깨우므로, 지적이 생기면 끝나는 명령을 둔다. `difit comment wait --port <port>`는 에이전트가 움직일 차례인 스레드가 있으면 그 스레드를 한 줄에 하나씩 JSON으로 찍고 끝나고, 없으면 생길 때까지 기다린다. 붙자마자 지금 차례인 스레드를 모두 찍으므로, 두 번 띄우는 사이에 생긴 지적도 다음 실행에서 받는다. 리뷰가 끝나면 아무것도 찍지 않고 0으로 끝난다. 끝났다는 알림 없이 연결이 끊기면 10초 동안 다시 붙으므로, 같은 포트로 다시 띄운 서버에는 기다리던 wait가 그대로 붙는다. `kill`로 멈춘 서버처럼 알림을 보내지 못하고 사라진 서버는 10초 뒤 연결 오류와 함께 1로 끝난다.

Claude Code 세션이 띄운 서버는 세션의 메시지 소켓(`CLAUDE_CODE_MESSAGING_SOCKET`)을 물려받는다. 이때는 리뷰어가 화면에서 저장해 새로 에이전트 차례가 된 스레드를 그 소켓으로 세션에 넣는다. 첫 줄은 스레드 id와 상태, 그리고 읽을 명령(`difit comment get --port <port> --format json`)이고, 이어지는 줄은 wait가 찍는 것과 같은 JSON이다. 명령을 띄워 두지 않아도 세션이 깨어난다.

## 에이전트 차례로 보는 스레드

- `[수정 중]`이고 마지막 메시지가 리뷰어(`User`)의 것이다. 에이전트가 `--comment`로 띄울 때 단 코멘트나 말로 답한 스레드는 세지 않는다. 상태만 보면 에이전트가 직접 단 코멘트가 영원히 에이전트 차례로 남는다.
- `[다시 수정 중]`이고, 새 fixup이 없고, 마지막 거절보다 뒤에 에이전트가 말한 적이 없다. 거절에 동의하지 않는 에이전트는 말로 답할 수 있어야 한다. 그러지 않으면 wait가 같은 스레드를 계속 돌려준다. 거절 시각은 리뷰어의 브라우저가, 메시지 시각은 서버나 에이전트가 적으므로 두 시계의 차이가 거절과 답 사이의 간격보다 크면 잘못 판단한다.
- `[승인 대기]`이고 마지막 메시지가 리뷰어의 것이며, 거절하지 않은 fixup이 모두 그 메시지보다 먼저 만들어졌다. 리뷰어는 승인이나 거절 대신 질문을 남기기도 하는데, 이 경우를 알리지 않으면 에이전트는 질문이 온 줄 모르고 승인만 기다린다. 메시지 순서만 보면 에이전트가 답글 없이 fixup만 올렸을 때 처음 지적이 그대로 마지막 메시지로 남으므로, fixup의 author date와 견준다. committer date는 rebase할 때마다 새로 찍혀서, 아직 답하지 않은 질문도 fixup보다 먼저 온 것으로 보이고 알림이 빠지므로 쓰지 않는다. 그 대가로 `--amend`로 fixup만 고쳐서는 차례가 끝나지 않으므로 에이전트는 말로도 답한다. 승인과 거절은 그대로 리뷰어가 한다.
- `[되돌림]`이고 되돌린 fixup이 아직 범위에 남아 있다. 0003은 되돌린 fixup을 마무리 때 버린다고 적었는데, 그러면 wait가 버릴 때까지 같은 스레드를 계속 돌려준다. 그래서 알림을 받으면 바로 버리게 한다.
- 고정할 커밋이 없는 리뷰(`.`, `working`, `staged`, `--pr`, 표준 입력)에는 상태가 없으므로, 리뷰어가 마지막으로 말한 스레드를 모두 센다.

`[승인됨]`·`[접힘]` 스레드는 리뷰어가 답글을 달아도 알리지 않는다. 에이전트가 할 일이 없는 상태라는 표를 그대로 따랐다.

## 세션에 넣는 것과 넣지 않는 것

화면이 저장하는 요청(`POST /api/comments`)에서만, 그 저장으로 새로 에이전트 차례가 된 스레드만 보낸다. 같은 스레드라도 리뷰어가 새 답글을 달거나 새 fixup을 다시 거절하면 다시 보낸다. 다음은 보내지 않는다.

- 에이전트가 `comment add`로 단 코멘트. 접은 뒤의 커밋으로 지적을 옮길 때 리뷰어의 메시지도 `comment add`로 복사되므로, 이 경로까지 보면 옮길 때마다 지적이 다시 온다.
- 리뷰어가 화면에서 직접 고친 fixup. 곧바로 승인되므로(0003) 에이전트가 할 일이 없다.
- 승인과 승인 취소.

서버를 다시 띄우면 화면이 기억하던 스레드를 한꺼번에 다시 올리므로, 그 가운데 에이전트 차례인 스레드가 메시지 하나에 함께 담겨 온다.

## 메시지 형식은 문서에 없다

Claude Code 문서(code.claude.com/docs/en/cross-session-messaging.md)는 소켓과 첫 줄의 인증만 적고, 메시지 형식은 적지 않는다. duru가 2026-10-13에 Claude Code 2.1.296에서 `{"type":"user","message":{"role":"user","content":"…"}}`만 세션에 들어가는 것을 확인했고, 이 포크에서는 2026-10-15에 2.1.300에서 같은 형식이 들어가는 것을 다시 확인했다. 형식이 맞든 틀리든 소켓은 아무것도 답하지 않으므로, 형식이 바뀌면 메시지가 조용히 사라진다. 그래서 소켓은 wait 위에 얹을 뿐이고 wait를 대신하지 않는다. 같은 스레드가 두 길로 오면 스레드 id와 상태가 같은 한 한 번만 답한다.

소켓에 닿지 못하면 stderr에 `Could not send the review update to the Claude Code session: …`을 남기고 리뷰를 이어 간다. 세션이 끝난 뒤에도 `--background`로 띄운 서버는 남아 있으므로, 이 실패가 리뷰를 멈추면 안 된다. 그 서버는 띄운 뒤 stderr를 버리므로 이 줄도 보이지 않는다.

테스트를 Claude Code 세션에서 돌리면 테스트가 띄운 서버가 그 세션에 메시지를 보내므로, 테스트 설정에서 두 환경 변수를 지운다.

## 검토한 다른 길

- 소켓만 쓰고 wait를 두지 않기: 지침은 가장 단순하지만, 형식이 바뀌면 모든 알림이 소리 없이 사라진다.
- wait를 SSE가 아닌 응답 하나로 기다리게 하기(long polling): Node의 `fetch`는 응답 머리를 5분 넘게 기다리지 않는다. SSE는 머리를 바로 보내고 30초마다 주석 한 줄을 보내 연결을 유지한다.
- 에이전트가 `comment get`을 주기적으로 다시 돌리기: 백그라운드 명령은 끝날 때만 깨우므로 결국 감시 도구(Monitor 같은)가 따로 필요하다. duru에서는 그 도구가 30분마다 멈추고 결과를 늦게 넘겼다.
- 모든 저장 경로에서 알리기: 위에 적은 대로 지적을 옮길 때마다 같은 지적이 다시 온다.
